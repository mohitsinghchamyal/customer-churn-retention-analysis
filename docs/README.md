## 1. Project Overview

Customer retention is an important measure of sustainable growth for e-commerce businesses. Understanding when customers stop purchasing, which segments show higher inactivity, and how purchasing behavior changes over time can help businesses develop more targeted retention strategies.

This project analyzes a synthetic Indian e-commerce marketplace dataset spanning 2015–2024. It demonstrates how a data analyst can build an end-to-end analytical workflow, from data exploration and feature engineering to SQL analysis and business intelligence reporting.

The project focuses on:

- Customer churn measurement using a 180-day inactivity definition.
- Customer purchase behavior and repeat-purchase patterns.
- Monthly performance and revenue trends.
- Cohort-based customer retention analysis.
- RFM (Recency, Frequency, Monetary) customer segmentation.
- Customer segmentation by acquisition channel, city, age band, and customer tier.
- Interactive dashboard development for business stakeholders.

**Important:** The dataset is simulated for portfolio and learning purposes. The project demonstrates analytical techniques rather than making claims about Amazon's actual customer behavior.

## 2. Business Objectives

The primary objectives are to:

1. Measure customer churn using a clearly defined inactivity threshold.
2. Identify customer segments with different churn and retention patterns.
3. Analyze repeat purchases and customer lifetime purchasing behavior.
4. Evaluate retention trends across customer acquisition cohorts.
5. Segment customers using RFM analysis.
6. Calculate business KPIs using Python and MySQL.
7. Present key findings through an interactive Power BI or Tableau dashboard.
8. Develop evidence-based recommendations for customer engagement and retention.

### Key business questions

- What proportion of eligible customers meet the 180-day churn definition?
- How does churn vary by customer tier, city, age band, and acquisition channel?
- How do monthly order volume and delivered revenue change over time?
- Which acquisition cohorts demonstrate stronger retention?
- What proportion of eligible customers make repeat purchases?
- Which RFM segments contribute the most delivered revenue?
- Which customer segments could be prioritized for re-engagement campaigns?

These questions should be answered using the actual outputs generated by the analysis rather than assumed in advance.

## 6. Business Definitions and KPIs

The project uses an analysis date of **December 31, 2024**.

### Churn definition

A customer is classified as churned when they have not made a delivered purchase during the 180 days preceding the analysis date, provided they have at least 180 days of observation since signup.

Customers without sufficient observation time should be excluded from the eligible churn denominator.

### Customer status

- **Active:** Most recent delivered purchase was fewer than 90 days ago.
- **At Risk:** Most recent delivered purchase was 90–179 days ago.
- **Churned:** Eligible customer with no delivered purchase during the defined 180-day inactivity window.
- **Never Purchased:** Customer with no delivered orders.

Never-purchased customers should be reported separately where appropriate, rather than automatically treating them as equivalent to previously active customers who became inactive.

### Order and revenue definitions

- **Delivered Order:** An order with `order_status = 'Delivered'`.
- **Net Delivered Order Value:** Order amount after discount for delivered orders; zero for returned or cancelled orders.
- **Repeat Purchaser:** Customer with at least two delivered orders.
- **Cohort:** Group of customers classified by the month of their first delivered purchase.

### Core KPIs

| KPI | Definition |
|---|---|
| Eligible Customers | Customers meeting the observation eligibility criteria |
| Churned Customers | Eligible customers meeting the 180-day churn definition |
| 180-Day Churn Rate | Churned customers / eligible customers |
| Repeat Customers | Customers with at least two delivered orders |
| Repeat Purchase Rate | Repeat customers / eligible customers, unless a different denominator is explicitly defined |
| Delivered Orders | Count of orders with delivered status |
| Net Delivered Revenue | Sum of net order value for delivered orders |
| Average Net Order Value | Net delivered revenue / delivered orders, using a consistent order-level definition |
| Cohort Retention Rate | Customers in a cohort purchasing in a later period / original cohort customers |

These definitions are specific to this portfolio project and are not represented as Amazon's internal business definitions.

## 7. Getting Started

This section explains how to run the project locally on macOS.

### Prerequisites

Install or configure the following tools as needed:

- Python 3.10 or newer.
- Visual Studio Code or another code editor.
- Git.
- MySQL Server 8+ and MySQL Workbench for database analysis.
- Power BI or Tableau for dashboard development.

**macOS note:** Power BI Desktop is a Windows application and does not run natively on macOS. Mac users can use Tableau Desktop, Power BI in a supported browser workflow where appropriate, or a supported Windows environment for Power BI Desktop.

### Step 1 — Clone the repository

Open Terminal on your Mac and run:

```bash
git clone https://github.com/mohitsinghchamyal/customer-churn-retention-analysis.git
```

Navigate to the downloaded project:

```bash
cd customer-churn-retention-analysis
```

Alternatively, if you already have the project downloaded, open the existing project folder in VS Code.

### Step 2 — Create a Python virtual environment

Create an isolated Python environment:

```bash
python3 -m venv .venv
```

Activate it on macOS:

```bash
source .venv/bin/activate
```

After activation, your Terminal prompt may display `(.venv)`.

To deactivate the environment later, run:

```bash
deactivate
```

### Step 3 — Install dependencies

Upgrade pip:

```bash
python -m pip install --upgrade pip
```

Install the project's dependencies:

```bash
python -m pip install -r requirements.txt
```

The `requirements.txt` file specifies the Python packages needed by the project.

If package installation fails, verify your Python version and check the error message before changing package versions.

### Step 4 — Verify the project files

Run:

```bash
ls
```

Confirm that you can see the `data`, `docs`, `python`, and `sql` directories and the `requirements.txt` file.

To inspect the available source datasets:

```bash
ls data
```

## 12. Power BI DAX Measures

The following examples assume tables named `customers` and `orders`, a one-to-many customer-to-order relationship where appropriate, and columns with the indicated names.

Adjust the expressions to the actual column types and relationships after importing the data.

### Eligible Customers

```dax
Eligible Customers =
CALCULATE(
    DISTINCTCOUNT(customers[customer_id]),
    customers[observation_eligible] = TRUE()
)
```

### Churned Customers

```dax
Churned Customers =
CALCULATE(
    DISTINCTCOUNT(customers[customer_id]),
    customers[observation_eligible] = TRUE(),
    customers[churned_180d] = TRUE()
)
```

### 180-Day Churn Rate

```dax
180-Day Churn Rate =
DIVIDE(
    [Churned Customers],
    [Eligible Customers]
)
```

Format this measure as a percentage.

### Delivered Orders

```dax
Delivered Orders =
CALCULATE(
    DISTINCTCOUNT(orders[order_id]),
    orders[order_status] = "Delivered"
)
```

### Net Delivered Revenue

```dax
Net Delivered Revenue =
CALCULATE(
    SUM(orders[net_order_value_inr]),
    orders[order_status] = "Delivered"
)
```

### Repeat Customers

```dax
Repeat Customers =
COUNTROWS(
    FILTER(
        VALUES(customers[customer_id]),
        CALCULATE(
            DISTINCTCOUNT(orders[order_id]),
            orders[order_status] = "Delivered"
        ) >= 2
    )
)
```

### Repeat Purchase Rate

```dax
Repeat Purchase Rate =
DIVIDE(
    [Repeat Customers],
    [Eligible Customers]
)
```

This definition uses eligible customers as the denominator. If the business question instead concerns repeat purchasing among customers who have purchased at least once, create a separate measure with that denominator and label it accordingly.

**Implementation notes**

- Confirm whether Boolean columns import as `TRUE/FALSE`, `1/0`, or text.
- Check whether the customer and order tables have the expected relationship.
- Ensure revenue calculations do not double-count orders.
- Confirm that all measures use consistent filters and definitions.

## 14. Business Recommendations to Evaluate

The following are hypotheses to investigate after running the analysis, not predetermined findings.

1. **Re-engagement campaigns:** Evaluate whether customers inactive for 90–179 days respond to targeted engagement before reaching the 180-day threshold.
2. **Acquisition channel analysis:** Compare repeat-purchase and churn rates across acquisition channels, accounting for differences in cohort age.
3. **Category-specific reminders:** Evaluate replenishment reminders for categories where repeat purchasing is behaviorally appropriate.
4. **High-value customer retention:** Assess whether personalized win-back offers are more effective for high-value, at-risk customers than broad discounts.

Recommendations should be refined using observed results, clearly stated assumptions, and appropriate validation.

## 16. Project Limitations

- The dataset is synthetic and cannot substantiate claims about Amazon's actual customer churn, revenue, or retention.
- The 180-day churn label is a point-in-time inactivity proxy, not a validated predictive model.
- Customers without sufficient observation time require careful eligibility handling; more rigorous longitudinal analysis should account for right-censoring.
- Segment-level differences are descriptive associations and do not establish causality.
- Return rates and other customer behavior measures require explicit definitions and consistent denominators.
- Dashboard results depend on correct data relationships, field types, and metric definitions.
- Recommendations should be evaluated through suitable experiments or additional analysis before being treated as proven business improvements.
